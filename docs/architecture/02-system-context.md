# 02 · System context

Status: Draft · Version 0.1

## Actors

Every request reaches the service layer as an `Actor` (`packages/server/src/http.ts`). `kind` is one of `user`, `agent`, `webhook`, `integration` or `guest`; background work writes audit rows as `system`.

| Actor kind     | Who                                                                                           | Enters through                                                | Authentication                                                                                        | Reach                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `user`         | A person using the web app                                                                    | The SPA, then `/api` and `/api/v1`                            | Session cookie `omr_session` (SameSite Lax), after an emailed code or OIDC SSO                        | Everything their grants allow; the only kind that may take human-only decisions                                  |
| `user`         | A person using the iOS app                                                                    | `/api/v1`                                                     | A device session sent as `Authorization: Bearer omr_s_…`; `sessions.client` names the device          | The same as the web, as a separate session that can be listed and revoked                                        |
| `agent`        | An AI agent acting for a person (Claude, Codex, Cursor and others)                            | `/mcp`                                                        | A personal access token `omr_pat_…` or an OAuth 2.1 access token, always minted by a signed-in person | `min(person's grants, credential ceiling)`; may write as a persona, always cosigned; never a human-only decision |
| `webhook`      | A script or service posting into one radar                                                    | `POST /hooks/:id/:token`, and `POST /hooks/email-capture/raw` | A per-webhook token in the URL (hashed at rest), or an HMAC from the email relay                      | Creates blips on one radar as its creator, marked not authored by them                                           |
| `integration`  | The Workshop & Web client portal                                                              | `/api/v1/helpdesk` only                                       | An `omr_int_…` credential plus the `X-OMR-Requester-Scope` header                                     | A whitelisted projection of requests on enrolled helpdesk radars                                                 |
| `guest`        | A signed-out visitor using guest support                                                      | `/api/guest-support`                                          | A capability token (stored as a SHA-256 hash) from `/start` or `/recover`                             | One conversation in the configured support queue                                                                 |
| `user` (admin) | Lucas or another admin (the admin bit is set from `ADMIN_EMAILS` when the account is created) | The SPA, `/api/admin/*`                                       | An ordinary session of a user with the admin bit                                                      | Approve, suspend and reinstate accounts, publish the plan catalog, manage the model catalog                      |
| `system`       | The worker process                                                                            | `packages/server/src/worker.ts`                               | None (same image and database, different argv)                                                        | Drains the outbox and delivery tables and runs the sweeps                                                        |

## Where the deployment sits

Cloudflare terminates the hostname and forwards through a `cloudflared` tunnel to Traefik in the cluster, namespace `onmyradar`. Traefik splits by path:

| Path                                                                                                     | Goes to                                  |
| -------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `/api`, `/oauth`, `/mcp`, `/hooks`, `/.well-known`, `/health`, `/r/`                                     | The API deployment `onmyradar`           |
| `/` with no `omr_session` cookie; exactly `/features`, `/agents`, `/waitlist`; `/features/*`, `/_site/*` | The marketing site                       |
| Everything else (SPA routes, `/assets`, `/sw.js`)                                                        | The UI deployment `onmyradar-ui` (nginx) |

The worker deployment `onmyradar-worker` has no public route; it serves only `GET /health/live` for its probe. The database is PostgreSQL 16; how it is hosted and replicated is the platform's concern and is not described in this repository.

## Trust boundaries

1. **Browser to API.** Cookies are `SameSite=Lax` and CORS never sends credentials; `refuseCrossSiteWrites` rejects cross-site writes to `/api` by `Sec-Fetch-Site` (it allows `same-site`) or `Origin`, and `/mcp` is outside that guard; a bearer credential is exempt because a page cannot attach one (`csrf.ts`).
2. **Agent to API.** Authority is the person's, clamped by the credential's ceiling. Consent is a screen only a signed-in person can submit.
3. **Public internet to the API.** The unauthenticated surfaces are the capture webhooks, the email ingress, the waitlist, the invite preview, the public radar pages, OAuth client registration, the Stripe webhook and the guest-support start. Most have their own rate limit or token check; public radar pages are gated only by an unguessable slug, and the invite preview by an HMAC.
4. **API to user-chosen URLs.** Only through `publicRequest` (principle P10).
5. **Client-supplied text to an agent.** Fenced at the MCP result boundary as data, not instructions; the control is that staff and agent text is not shown to the client without the owner (the owner's own `client` reply publishes at once).
6. **Pod to storage.** Attachment bytes go browser to storage directly; the pod handles bytes only for inbound email, image viewing for agents and a few bounded reads (see `components/storage.md`).

## System of record

| Fact                                   | Owner                                                | OMR's copy                                                         |
| -------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------ |
| Who a person is                        | OMR (`users`); SSO only proves control of an address | Matched by email; `identities` is written but never read           |
| What a person may read                 | OMR (`radars`, `radar_members`, `topic_members`)     | Computed on every request                                          |
| Attachment bytes                       | Object storage                                       | Metadata in `attachments`                                          |
| An agent's prompt, memories and briefs | OMR (`agents` and `agent_*`)                         | A repo copy of a brief is the mirror's target, never imported back |
| Client-visible helpdesk text           | OMR; staff and agent text released by the owner      | The portal reads only comments whose visibility is `client`        |
| The contract vocabulary                | `packages/contract`                                  | The iOS repo vendors a generated snapshot                          |
| What is deployed                       | the GitOps repository (Fleet)                        | Release CI sets only the image digests (by `kubectl set image`)    |
